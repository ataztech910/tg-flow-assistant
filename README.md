# BotFlow POC

A Telegram bot driven entirely by `flow.yaml` — no hardcoded flow logic in the bot.

## Run — multiple bots (the real thing)

```sh
deno run --allow-net --allow-env --allow-read --allow-write --allow-run --allow-import server.ts
```

(`--allow-run` is for the AI edit panel — it lets Kitana spawn the local `claude` CLI. Omit it if
you don't need that and don't want to grant it.)

Opens a dashboard at `http://localhost:8000`. On startup it loads and starts every bot already
saved under `bots/<id>/` (each bot's own `meta.json` + `flow.yaml`). To add a bot: paste a token
from BotFather and a `flow.yaml` into the form on the home page and submit — the server validates
both (schema + reference checks, then a real `getMe` call), saves `bots/<id>/{meta.json,flow.yaml}`,
and starts polling immediately, all in this same process (see "How it works" below for why this
doesn't need webhooks or a public domain at this scale). Each bot gets its own page at
`/bots/<id>` with a live, draggable React Flow diagram of its flow, Start/Stop, its recently
collected data, and a version history.

A bad or revoked token on one bot never takes the others down — `BotManager` isolates each bot's
`bot.start()` failure and just marks that one "stopped" (see `bot-manager.ts`).

## Edit a flow from the dashboard

Click any node card on the diagram (not drag) to open its panel — two tabs:

- **Edit** — a plain form matching that node's fields (mirrors `schema.ts`, no YAML involved).
  Save writes the whole flow back via `POST /bots/:id/flow`. Also: "+ Add node" (top-right of the
  diagram), "Set as start", "Delete node".
- **Ask AI** — type what you want changed (or use a quick-action button) and it's sent to
  `ai-editor.ts`, which calls `@kitana-sdk/core` — routed through the local `claude` CLI's
  subscription auth by default (`claude auth login`, no API key needed), falling back to
  `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` if set. The model only ever returns text (Kitana disables
  all its tools) — we validate the result against `schema.ts`+`flow-check.ts` ourselves before
  saving, with one automatic retry (error fed back to the model) if the first attempt doesn't pass.

Every accepted edit (form or AI) archives the previous `flow.yaml` under `bots/<id>/versions/`
before overwriting it — nothing is ever lost. The dashboard's "Version history" section lists past
snapshots with a one-click **Restore** (which itself creates a new snapshot first, so restoring is
undoable too).

## Run — a single bot (quick local testing)

```sh
TELEGRAM_TOKEN=your_token \
deno run --allow-net --allow-env --allow-read --allow-write --allow-import bot.ts
```

Reads `./flow.yaml` directly, no server/dashboard. Useful for quickly trying a flow with a single
bot without going through the creation form.

- `TELEGRAM_TOKEN` — from BotFather.
- `TELEGRAM_PROVIDER_TOKEN` — only needed if a `payment` node uses a real currency (`USD`, `EUR`,
  ...) instead of Telegram Stars. Get it from BotFather → your bot → **Payments** → connect a
  provider and use its test token. The shipped demo flow uses `currency: "XTR"` (Telegram Stars),
  which needs no provider token at all — works out of the box.

## Validate a flow before uploading/running it

```sh
deno run --allow-read --allow-env validate.ts flow.yaml
```

Checks the YAML against the schema (`schema.ts`) and makes sure every `next`/`on_error`/`on_fail`
points at a node that actually exists. This is the same check meant to run on any `flow.yaml`
generated by an LLM — see `dsl-rules.md`.

## Look at a flow before running it

The `/bots/<id>` dashboard page (see above) shows a live, draggable diagram via React Flow —
`flow-to-reactflow.ts` is the deterministic converter behind it (no AI involved, a direct
rendering of the YAML's structure). Start the server and open the bot's page to see it.

## Test a flow without Telegram at all

```sh
deno run --allow-read --allow-write --allow-net test-run.ts flow.yaml
```

An interactive terminal walkthrough of the flow — it plays the bot's side, you reply as the user
(pick buttons by number, type free text for `input` nodes, confirm/skip simulated payments).
`webhook` and `collect` nodes run for real (actual HTTP calls, actual writes to
`data/leads.jsonl`), so this exercises the same code path a live Telegram bot would, just without
needing a bot token or the Telegram app. Good for quickly sanity-checking a flow an LLM generated,
right after `validate.ts` confirms it's structurally valid.

## How it works

```
                          ┌─ bots/<id>/flow.yaml ─→ FlowEngine ─→ createTelegramBot ─→ Telegram
server.ts (BotManager) ───┼─ bots/<id2>/flow.yaml ─→ FlowEngine ─→ createTelegramBot ─→ Telegram
                          └─ bots/<id3>/flow.yaml ─→ FlowEngine ─→ createTelegramBot ─→ Telegram
```

Each bot gets its own `FlowEngine` instance (isolated per-user state) and does its own Telegram
long-polling *concurrently in the same process* — polling is async and doesn't block the Event
Loop, and Telegram only allows one poller per bot token anyway, so this is both simple and correct
at small-to-medium scale. No webhooks or public domain needed yet (see TASKS.md "Потом — масштаб"
for when that stops being true).

Within one bot's flow:
```
flow.yaml  →  FlowEngine  →  Telegram
                  │
                  ├─ collect → store.ts (bots/<id>/data/leads.jsonl, kept by us)
                  └─ webhook → external HTTP API (forwarded to an outside service)
```

- `schema.ts` — Zod schema for `flow.yaml`, the single source of truth for what's valid
- `flow-check.ts` — reference-integrity + reachability check (every `next` points somewhere real),
  shared by `validate.ts` and bot creation in `bot-manager.ts`
- `validate.ts` — CLI that checks a flow file against `schema.ts` + `flow-check.ts`
- `engine.ts` — parses the YAML, holds per-user FSM state + collected data in memory, executes
  nodes; takes a `dataDir` so each bot's `collect` writes stay isolated
- `store.ts` — tiny internal storage for `collect` nodes (append-only JSON lines)
- `telegram-adapter.ts` — wires a `FlowEngine` to a grammy `Bot` (messages, buttons, payments);
  shared by both single-bot `bot.ts` and multi-bot `bot-manager.ts` so the handler logic exists once
- `bot-manager.ts` — runs multiple bots in one process (see diagram above), persists each to
  `bots/<id>/`, isolates start failures so one bad token can't take the others down
- `server.ts` — HTTP dashboard: create bots, view each one's live diagram and collected data
- `views.ts` — HTML templates for the dashboard (plain server-rendered HTML, no framework)
- `flow.yaml` — the demo bot's flow (screens, text, data collection, webhooks, payments) — a
  multi-bot setup has one of these per bot, under `bots/<id>/flow.yaml`
- `dsl-rules.md` — the rules document to hand to any LLM so it can generate a valid `flow.yaml` for you

## Changing the flow

Write a prompt for any LLM using `dsl-rules.md`, get a `flow.yaml` back, run `validate.ts` on it,
fix anything it flags, then drop it in and restart the bot. No TypeScript changes needed.

## Node types

`message`, `menu`, `input`, `webhook`, `collect`, `payment`, `condition`, `subscribe`, `event` —
plus optional media (photo/video/audio/document/voice) on `message`/`menu`. Media can be a public `http(s)://` URL
(Telegram fetches it) or a file uploaded via the node panel's upload button — the bot sends that
one itself (`bots/<id>/media/`), so it works even though this server has no public URL of its own.
Full reference and examples in [`dsl-rules.md`](./dsl-rules.md).

## Testing the demo flow end-to-end

The shipped `flow.yaml` includes a "🧪 Full demo" path from the welcome menu that exercises all
four capabilities:

1. `/start` → **Full demo** → answer the name/email prompts (`input` nodes)
2. Data is saved locally to `data/leads.jsonl` (`collect` node)
3. Data is POSTed to the `forward_to_crm` webhook, which points at `http://localhost:8787/leads` by
   default — run `deno run --allow-net mock-crm.ts` in another terminal first and watch it print
   the incoming request. Swap the URL in `flow.yaml` for a real service (or a fresh
   [webhook.site](https://webhook.site) URL) whenever you want to test against something real.
4. A Telegram Stars invoice for 10 ⭐ is sent (`payment` node) — pay it (Stars can be bought/tested
   directly in the Telegram client) and confirm the flow resumes on `payment_success`

## Deploying to production (Deno Deploy)

Editing (dashboard, node form, AI chat, file uploads, version history) only ever happens locally,
against `server.ts` — it needs local disk writes and the ability to spawn the `claude` CLI, neither
of which Deno Deploy's isolates support. Production deploys a **different, much smaller
entrypoint** — `server-prod.ts` — that only serves already-finished `flow.yaml` files over Telegram
webhooks. There is no dashboard in this file at all; visiting the deployed URL directly just shows
a static "nothing to see here" response.

1. Finish editing locally, make sure `bots/<id>/flow.yaml` (and `bots/<id>/media/` if used) are
   how you want them — these get shipped as regular files as part of the deploy.
2. Provision a Deno KV database and assign it to the app — **this does not happen automatically**,
   and `collect` nodes fail silently (the message is swallowed by `bot.catch`, the user just gets
   no reply) without it:
   ```sh
   deno deploy database provision botflow-kv --org=<org> --kind denokv
   deno deploy database assign botflow-kv --org=<org> --app=<app>
   ```
   One-time setup per app. `deno deploy database list --org=<org>` confirms the assignment.
3. In your Deno Deploy project (dash.deno.com), set these as environment variables/secrets:
   - `PROD_BOT_IDS` — comma-separated bot ids to activate, e.g. `8984073292`
   - `BOT_TOKEN_<id>` — that bot's token, one var per id in `PROD_BOT_IDS`
   - `PUBLIC_URL` — this deployment's own base URL, e.g. `https://yourproject.deno.dev`
   - optional: `BOT_PROVIDER_TOKEN_<id>` (real-currency payments), `WEBHOOK_SECRET` (recommended —
     checked against Telegram's `X-Telegram-Bot-Api-Secret-Token` header on every webhook call),
     `ADMIN_SECRET` (lead export, see below), `EVENT_SECRET` (monitoring/alerts, see below)
4. Deploy — this project uses the `deno deploy` subcommand built into the Deno CLI itself (not the
   separate `deployctl` package):
   ```sh
   deno deploy --prod
   ```
   **`--prod` is required** — without it, every deploy only updates a throwaway preview URL
   (`botflow-prod-<hash>.tofo.deno.net`) and the stable production domain
   (`botflow-prod.tofo.deno.net`) stays on whatever was last actually promoted. `PUBLIC_URL` (see
   below) must point at the stable domain, not a preview URL, or the webhook breaks on every deploy.
   First-time setup: `deno deploy create . --org=<org> --app=<app> --source=local --entrypoint=server-prod.ts --region=us`
   (interactive if you omit the flags — annoying to navigate, the explicit flags are easier).
5. On startup, `server-prod.ts` calls `setWebhook` for every configured bot automatically — no
   manual Telegram-side setup needed. Check the deploy logs for `Bot <id> (@username) webhook set
   to ...` per bot.
6. Message the bot on Telegram — it should reply via the webhook, no polling involved.

`collect` nodes write to **Deno KV** in this entrypoint (`FlowEngine` is constructed with `kv:<id>`
as its data dir — see `store.ts`) — Deno Deploy's isolates have no persistent local disk, so once
step 2 above is done, this is where leads live. `server-prod.ts` probes `Deno.openKv()` at startup
and only takes this path if it actually succeeds, so a misconfigured or missing database degrades
to the disk-based path below instead of crashing every `collect` node — but on Deploy specifically,
that fallback path has no persistent disk either, so leads are simply lost across isolate restarts
until step 2 is done properly. Check the logs.

### Exporting collected leads

There's no dashboard in production, so `collect` data (which now always includes real
`telegram_id`/`telegram_username`/`telegram_first_name`/`telegram_last_name`/
`telegram_language_code` fields, not just whatever an `input` node happened to ask for — see
`dsl-rules.md`) needs its own way out. Set `ADMIN_SECRET` (any random string — `openssl rand -hex
24`, then `deno deploy env add ADMIN_SECRET <value>`) and hit:

```sh
curl -H "X-Admin-Secret: <value>" https://<your-app>.deno.net/admin/leads/<bot-id>
curl -H "X-Admin-Secret: <value>" "https://<your-app>.deno.net/admin/leads/<bot-id>?format=csv" -o leads.csv
```

The secret goes in a header, not the URL, so it doesn't end up in access logs. Unset `ADMIN_SECRET`
and the route 404s outright rather than sitting open — this is off by default. Works identically on
Docker/Cloud Run/AWS, reading from `bots/<id>/data/leads.jsonl` there instead of KV.

### Monitoring and alerts (pushing events *into* a bot)

`webhook` nodes call *out*; this is the other direction — an external system (a CI pipeline, an
OpenTelemetry collector, a cron job, anything that can POST JSON) pushes an event in, and everyone
who opted in via a `subscribe` node gets it as a Telegram message. Two new node types, no dashboard
support needed since it's just YAML — see `dsl-rules.md`'s "Monitoring / alerts" pattern for the
full example. Once the flow has a `subscribe` node and an `event` node (say, `deploy_failed`), set
`EVENT_SECRET` (same pattern as `ADMIN_SECRET` — `openssl rand -hex 24`, then `deno deploy env add
EVENT_SECRET <value>`) and have the external system hit:

```sh
curl -X POST https://<your-app>.deno.net/event/<bot-id>/deploy_failed \
  -H "X-Webhook-Secret: <value>" \
  -H "content-type: application/json" \
  -d '{"service":"api","branch":"main","error":"connection refused"}'
```

The `event` node's `message` template renders against that JSON body (`{{service}}`, `{{branch}}`,
`{{error}}` above — not `state.data`, since there's no user or prior flow state involved) and gets
sent to every subscriber. Response is `{"sent": N, "subscribers": M}` — `sent` can be lower than
`subscribers` if Telegram rejects a delivery (e.g. someone blocked the bot); check the logs for
which. Separate secret from `ADMIN_SECRET` on purpose — this one gets handed to whatever external
system is triggering it, so it should be rotatable independently of the leads-export secret.

## Deploying elsewhere (Docker, Google Cloud Run, AWS)

`server-prod.ts` isn't tied to Deno Deploy — it's a plain `Deno.serve` HTTP server, so any platform
that runs a container works. `Deno.openKv()` is still an unstable API off Deno Deploy's own managed
runtime (it needs an `--unstable-kv` flag this project deliberately doesn't pass), so `server-prod.ts`
detects that at startup and `collect` nodes write to a local file instead —
`bots/<id>/data/leads.jsonl`, the same format and location `server.ts` uses locally. A real
container (unlike Deno Deploy's isolates) has an actual filesystem, so this just needs to sit on a
persistent volume, same as `flow.yaml` and media.

### Docker / any VPS

```sh
docker build -t botflow .
docker run -p 8000:8000 --env-file deploy.env -v botflow-data:/app/bots botflow
```

The image only ever imports `server-prod.ts`'s own dependency graph — no dashboard code runs, same
as on Deno Deploy. The `-v botflow-data:/app/bots` volume is what makes `bots/<id>/flow.yaml`,
uploaded media, and `bots/<id>/data/leads.jsonl` survive a container restart — skip it and you get
a fresh empty state every time. Same env vars as the Deno Deploy section above (`PROD_BOT_IDS`,
`BOT_TOKEN_<id>`, `PUBLIC_URL`, optional `WEBHOOK_SECRET`) via `--env-file` or `-e` — no database
provisioning step needed here, unlike Deno Deploy.

Before the first run, copy each bot's `flow.yaml` (and `media/` if used) into the volume — e.g.
`docker run --rm -v botflow-data:/app/bots -v "$(pwd)/bots":/host alpine cp -r /host/. /app/bots/`
once, or mount your local `bots/` directory directly instead of a named volume if you're fine with
host-path storage: `-v "$(pwd)/bots":/app/bots`.

### Google Cloud Run

Cloud Run runs the same Docker image; the wrinkle is its filesystem is ephemeral per revision
unless you attach a volume:

```sh
gcloud run deploy botflow \
  --source . \
  --port 8000 \
  --set-env-vars PROD_BOT_IDS=<id>,PUBLIC_URL=https://<service>-<hash>.<region>.run.app \
  --set-secrets BOT_TOKEN_<id>=botflow-bot-token:latest
```
(`--source .` builds from the `Dockerfile` directly — no separate `docker build`/push step needed.
Put the token in Secret Manager first: `gcloud secrets create botflow-bot-token --data-file=-`.)
For persistence, mount a [Cloud Storage FUSE volume](https://cloud.google.com/run/docs/configuring/services/cloud-storage-volume-mounts)
at `/app/bots`, or accept that `collect` data resets on redeploy for a low-stakes bot.
`PUBLIC_URL` must be the service's own stable URL — Cloud Run assigns one per service, not per
revision, so unlike Deno Deploy there's no separate "preview vs. production" domain to worry about.

### AWS (App Runner or ECS/Fargate)

- **App Runner** — closest to Cloud Run: point it at the `Dockerfile`, set the same env vars
  (`PROD_BOT_IDS`, `BOT_TOKEN_<id>`, `PUBLIC_URL` = the App Runner-assigned URL, `WEBHOOK_SECRET`)
  via the console or `apprunner.yaml`. App Runner has no built-in persistent volume — for real
  persistence, swap `store.ts`'s `saveLead` to write to DynamoDB or S3 instead of the local
  `leads.jsonl` file (same pattern as the existing `kv:` branch, different backend).
- **ECS/Fargate** — same image, add an EFS volume mount at `/app/bots` in the task definition for
  actual persistence (Fargate supports EFS natively, unlike App Runner). Set env vars via the task
  definition's `environment`/`secrets` (the latter pulling from Secrets Manager for `BOT_TOKEN_<id>`).

In every case the deploy step itself is just "get this Docker image running somewhere with these
env vars and a volume at `/app/bots`" — the app code doesn't know or care which platform it's on.

## Project structure

```
flow.yaml         # demo bot's flow definition (screens, inputs, webhooks, payments)
schema.ts         # Zod schema — the formal DSL definition
flow-check.ts      # reference-integrity + reachability check, shared by validate.ts and bot-manager.ts
validate.ts        # CLI: validates a flow.yaml against schema.ts + flow-check.ts
engine.ts          # FlowEngine: YAML → FSM, executes nodes, stateless output
store.ts           # internal storage for `collect` nodes
telegram-adapter.ts # wires a FlowEngine to a grammy Bot — shared by bot.ts and bot-manager.ts
bot.ts             # single-bot CLI runner (reads ./flow.yaml, no dashboard)
bot-manager.ts     # runs multiple bots in one process; persists each under bots/<id>/, versioned saves
ai-editor.ts       # AI-assisted flow.yaml edits via @kitana-sdk/core, with retry-validation
server.ts          # LOCAL dashboard: create/edit bots, AI chat, version history, collected data
server-prod.ts     # PRODUCTION entrypoint (Deploy/Docker/Cloud Run/AWS) — webhooks only, no dashboard
views.ts           # HTML templates + client script for the dashboard (node form + AI panel)
test-run.ts        # interactive terminal walkthrough of a flow, no Telegram needed
flow-to-reactflow.ts # flow.yaml -> React Flow graph (used by the live dashboard)
mock-crm.ts        # local stand-in CRM server for testing webhook nodes offline
dsl-rules.md       # rules doc for generating flow.yaml with any LLM
Dockerfile         # container image for server-prod.ts (Docker/Cloud Run/AWS)
deploy.env.example # template for deploy.env (gitignored — real tokens never committed)
TASKS.md           # backlog
LICENSE            # MIT
README.md          # this file
bots/<id>/         # created at runtime by server.ts — meta.json, flow.yaml, data/leads.jsonl per bot
```
