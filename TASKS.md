## Сейчас (закрыто — все три пункта готовы)

- [x] **Виртуальный прогон флоу (как test run в n8n) — визуальный** — уточнение: имелся в виду
      прогон поверх диаграммы, не терминал. Панель "Test run" на `/bots/:id` управляет тем же живым
      `FlowEngine`, что обслуживает реального бота, через зарезервированный `userId = -1`
      (реальные Telegram id всегда положительные). Активный узел подсвечивается и в него
      автоматически центрируется вид (`useReactFlow().fitView`) — при заходе на страницу это же
      сразу показывает `start_node`, не только во время прогона. `webhook`/`collect` выполняются
      по-настоящему, платёж — по кнопке "Simulate successful payment". `test-run.ts` (терминал)
      остаётся отдельным headless-инструментом, не заменён.
- [x] **Визуальная проверка флоу (Mermaid)** — `mermaid.ts`: детерминированный конвертер
      `flow.yaml → Mermaid`, разные фигуры по типам узлов, пунктир для `on_error`/`on_fail`.
      Проверено на демо-флоу, опубликовано как артефакт.
- [x] **Процесс создания бота (визуальный)** — `server.ts` + `bot-manager.ts` + `views.ts`:
      HTTP-дашборд, форма (токен + flow.yaml) → валидация (`schema.ts` + `flow-check.ts` + реальный
      `getMe`) → `bots/<id>/{meta.json,flow.yaml}` → бот стартует в этом же процессе. `/bots/<id>` —
      живая Mermaid-диаграмма (та же `flowToMermaid` из `mermaid.ts`) + последние собранные данные +
      Start/Stop. При рестарте сервера все боты из `bots/` поднимаются автоматически.
      Нашли и починили по пути: `bot.start()` с невалидным/отозванным токеном кидал необработанную
      ошибку и ронял **весь процесс** (все боты разом) — теперь каждый запуск изолирован
      (`BotManager.launch`), плохой токен просто помечает своего бота "stopped".
      **Известный гэп:** токен в `meta.json` хранится в открытом виде — ок для локального POC,
      шифрование — часть будущей фазы Auth.

## Дальше — AI-редактор флоу в дашборде (Tiptap AI Toolkit-style)

- [x] **Reload flow без рестарта** — `bot-manager.ts`: `BotManager.reloadFlow(id)` перечитывает
      `bots/<id>/flow.yaml` с диска, валидирует (`assertValidFlow` — общий хелпер, теперь и
      `createBot`, и `reloadFlow` используют одну и ту же проверку), применяет на уже работающий
      `engine.loadFlow()` — без даунтайма остальных ботов. Кнопка "↻ Reload flow" на дашборде.
      Ближайший практический workflow: правки в `flow.yaml` делаются через Claude Code напрямую
      (см. ниже), затем жмётся эта кнопка.
- [x] **Версионирование флоу** — `bot-manager.ts`: `saveFlow`/`archiveCurrentFlow`/`listVersions`/
      `restoreVersion`. Любое принятое изменение архивирует текущий `flow.yaml` в
      `bots/<id>/versions/<ts>__<label>.yaml` перед перезаписью; невалидные правки отклоняются без
      создания версии; restore сам архивируется (откат обратим). Секция "Version history" на
      дашборде. Проверено end-to-end через реальные HTTP-запросы к серверу.
- [x] **Точки входа/выхода + форма свойств узла (n8n-style)** — клик по карточке на графе (не
      драг) открывает панель с полями конкретного типа узла (зеркалят `schema.ts`), включая
      редактируемый список кнопок, "Set as start" и "Delete node". "+ Add node" с выбором типа.
      Сохранение шлёт весь объект `flow` на `POST /bots/:id/flow` → `saveFlow`. Удаление узла, на
      который остались ссылки, корректно отклоняется валидатором (не пытаемся тихо чинить сами).
      Известное ограничение: `headers`/`body`/`save_response_as` у `webhook` пока не редактируются
      формой (только текстом/AI) — заметно небольшой процент случаев, не блокер.
- [x] **Чат-редактор флоу (как Tiptap AI Toolkit)** — `ai-editor.ts` + вкладка "Ask AI" в панели
      узла. Зовёт `@kitana-sdk/core` (роутер `chain: ['claude','codex','ollama','api-key']`,
      по умолчанию бесплатно через `claude auth login`, фоллбэк на `ANTHROPIC_API_KEY`/
      `OPENAI_API_KEY`). Промпт = `dsl-rules.md` + текущий `flow.yaml` + (если узел выбран) на
      каком узле фокус + инструкция пользователя; модель отвечает только текстом (Kitana отключает
      ей все инструменты), мы сами валидируем ответ через `schema.ts`+`flow-check.ts` с одним
      автоматическим повтором (текст ошибки скармливается обратно), затем `saveFlow` (версия
      архивируется как обычно).
      **Проверено вживую, реальным вызовом:** инструкция "Add a new message node called pricing...
      and add a button on welcome" → Claude через `claude -p` (~7 сек) → корректный YAML с новым
      узлом и кнопкой, прошёл валидацию с первого раза, сохранился, версия заархивирована.
      `deno.json` теперь в проекте (`deno add npm:@kitana-sdk/core`), нужен `--allow-run` при
      запуске `server.ts`.

## Потом — прод на Deno Deploy

Целевая платформа — классический Deno Deploy, подтверждено пользователем (деплой через
`deployctl` из терминала). Ключевое решение: **редактирование только локально, прод — read-only
деплой готовых `flow.yaml`** (идея пользователя, аналогия с тем, как GraphQL-плейграунд прячут в
проде).

- [x] **`server-prod.ts`** — отдельный тонкий entrypoint, без единого `/bots`-роута дашборда
      вообще (не спрятаны условно — их просто нет в файле). Конфиг ботов через env
      (`PROD_BOT_IDS`, `BOT_TOKEN_<id>`, `PUBLIC_URL`, опционально `WEBHOOK_SECRET`), `flow.yaml`
      читается как обычный ассет деплоя. Проверено локально: валидация env (понятные ошибки),
      чтение `flow.yaml`, сборка `FlowEngine`+бота, падает ровно на реальном вызове Telegram с
      фейковым токеном (`bot.init()` требует валидный токен — так и должно быть).
- [x] **Вебхуки вместо long polling** — `webhookCallback(bot, "std/http")` из grammy, `Deno.serve`
      маршрутизирует `POST /webhook/:id`. Важная деталь, которую легко упустить: `bot.init()`
      нужно вызвать явно перед первым апдейтом — в polling-режиме (`bot.start()`) это скрыто
      внутри, в webhook-режиме `handleUpdate()` иначе падает с "Bot not initialized!".
- [x] **`collect` в проде — Deno KV, не файл** — `store.ts`: `saveLead(dataDir, ...)` при
      `dataDir` вида `"kv:<id>"` пишет в `Deno.openKv()` вместо диска (эфемерного на Deploy).
      `engine.ts` не менялся — просто получает другую строку. Проверено локально записью+чтением
      через реальный `Deno.openKv()`.
- [x] **Прод-инцидент: `Deno.openKv is not a function`, бот молчал на payment-узле** — локальная
      проверка выше была неполной: на новой единой `deno deploy` платформе `Deno.openKv()` не
      работает "из коробки" даже в проде — БД нужно явно создать и привязать к приложению
      (`deno deploy database provision --kind denokv` + `database assign`), иначе на любом
      `collect`-узле бросается исключение, которое молча съедает `bot.catch` — пользователь просто
      не получает ответа, никакого сообщения об ошибке. Уронило именно payment-флоу, потому что
      перед оплатой стоял `collect`. Исправлено: (1) создана и привязана `botflow-kv` для
      `botflow-prod`; (2) `server-prod.ts` больше не считает `kv:` безусловным — при старте реально
      пробует `Deno.openKv()` и только при успехе использует KV, иначе откатывается на
      `bots/<id>/data/leads.jsonl` на диске (актуально для Docker/Cloud Run/AWS — там
      `Deno.openKv()` всё ещё unstable API без флага, которого мы сознательно не передаём).
      Задокументировано в README (шаг provision+assign в секции Deno Deploy, обновлена секция
      "Deploying elsewhere").
- [x] **Живой деплой выполнен и проверен** — не `deployctl` (отдельный пакет), а `deno deploy`,
      встроенный в сам Deno CLI 2.7.14 — новый продукт с `sandbox`/`database` подкомандами, другой
      набор флагов. По пути споткнулись дважды: (1) `--entrypoint` через `deno deploy create`
      почему-то не сохранился — пофиксили руками в "Edit app configuration" в дашборде; (2) без
      флага `--prod` деплой уходит только в preview (`<app>-<hash>.<org>.deno.net`), стабильный
      домен (`<app>.<org>.deno.net`) не обновляется — нужно `deno deploy --prod`. Бот отвечает на
      `/start` через стабильный домен, `getWebhookInfo` подтверждает регистрацию.
- [ ] **State пользователя (`FlowEngine.state`) не переживает между изолятами** — если юзер
      посреди диалога (ждём ответ на `input`), а следующий вебхук-запрос попадёт в другой
      изолят — состояние потеряно. **Не решено** (в отличие от `collect`, здесь пока просто `Map`
      в памяти `server-prod.ts`, как и в dev). Нужен тот же переезд на Deno KV, что уже сделан для
      лидов, но для сессионного состояния — отдельная задача, `FlowEngine` придётся научить читать
      состояние асинхронно, сейчас `state.get()`/`state.set()` синхронные.
- [ ] Очередь на исходящие сообщения с троттлингом (лимиты Telegram: ~30/сек общий, 1/сек на чат)
- [ ] Медиа в проде — если "деплоим как есть" не годится для больших файлов (лимит Deploy на
      деплой ~1GB суммарно), тогда S3-совместимое хранилище (R2/S3/B2) с публичным URL, `media.url`
      просто `http(s)://`, `InputFile` не нужен вообще
